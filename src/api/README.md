# Временный бекенд на Google AppScript

Бекенд сделан на гуглотаблицах (Google AppScript). **Никакой логики на беке — только хранение данных.** Вся логика подсчёта, сортировки и копирования — на фронтенде.

---

## Поднятие бэка

### 1. Создать новую гуглотаблицу

Зайди в Google Sheets, создай пустую таблицу.

### 2. Открыть AppScript

Меню: **Расширения → Apps Script**

### 3. Скопировать код

Скопируй **весь** код из файла `src/api/googleAppScriptBackend.gs` и вставь в редактор.

### 5. Опубликовать WebApp

[Инструкция по деплою](https://seoneurons.com/create-contact-us-page/#34-deploying-the-script-as-a-web-app)

- Нажми **Развернуть → Новое развертывание**
- Тип: **Веб-приложение**
- Доступ: **Все (в том числе анонимные)**
- Нажми **Развернуть**

После деплоя скопируй **Идентификатор развертывания**.

### 6. Прописать переменную окружения

Создай файл `.env` в корне проекта и добавь:

```env
PUBLIC_PROD_GOOGLE_APPSCRIPT_ID=<идентификатор_развертывания>
```

### 7. Сбилдить и задеплоить

```bash
npm run build
```

Артефакты из `/dist` залить на хостинг (Vercel, Netlify, Cloudflare Pages и т.д.).

### 8. Заполнить таблицу

После первого запроса скрипт **автоматически создаст** нужные листы:

| Лист       | Назначение                                                              |
| ---------- | ----------------------------------------------------------------------- |
| `Buffs`    | Очередь баффов (id, nick, type, buff, endAt, ...)                       |
| `History`  | История выдач (id, recipient_id, recipient, type, giver, percent, time) |
| `Givers`   | Статистика доноров (nick, total, last_buff)                             |
| `Nicks`    | Сохранённые ники (nick)                                                 |
| `Template` | Шаблон копирования в чат (key, value)                                   |

Ничего заполнять вручную не нужно — данные попадают в таблицы через API.

## API — эндпоинты

Все запросы на один URL веб-приложения с параметром `?type=`.

> **Порядок раскатки:** сначала обновить GAS, затем фронт. Новый фронт блокирует запись, если бэкенд не поддерживает `rev`.

### GET `?type=version`

Быстрая проверка ревизии:

```json
{ "ok": true, "rev": 42, "epoch": "1700000000000abc" }
```

`rev` увеличивается на каждом `save`. `epoch` меняется только при сбросе ScriptProperties/пересоздании проекта. Фронт опрашивает `version` для синхронизации.

### GET `?type=state`

Данные очереди: `buffs`, `givers`, `nicks`, `template`. Кеш — 1 час. `&force=1` — читать мимо кеша.

### GET `?type=history`

История транзакций. Кеш — 30 минут. `&force=1` — читать мимо кеша.

### GET `?type=all`

Все данные сразу, без кеша. Удобно для скриптов:

```json
{
  "ok": true,
  "rev": 42,
  "epoch": "1700000000000abc",
  "buffs": [...],
  "history": [...],
  "givers": { "nick": { "total": 1, "last_buff": 1234567890 } },
  "nicks": ["nick1", "nick2"],
  "template": {...}
}
```

### POST `?type=save`

Сохраняет изменения. Тело — JSON:

```json
{
  "buff": {...},                    // upsert одной записи по id
  "expectedAppliedCount": 2,        // защита от одновременного apply
  "deleteBuffId": "b_123",          // удалить одну запись
  "historyEntry": {...},            // добавить запись в History
  "giverStat": {                    // обновить счётчик и дату для ника
    "nick": "Vi007",
    "ts": 1234567890
  },
  "nick": "Vi007",                  // добавить ник если нет
  "nick2": "Vi008",
  "template": {...},                // заменить шаблон

  "buffs": [...]                    // legacy: полная замена листа Buffs
}
```

Можно передать одно поле или сразу несколько. Ответ содержит `rev`, `epoch` и свежие данные всех таблиц:

```json
{
  "ok": true,
  "rev": 43,
  "epoch": "1700000000000abc",
  "buffs": [...],
  "history": [...],
  "givers": {...},
  "nicks": [...],
  "template": {...}
}
```

Если `expectedAppliedCount` не совпал с текущим `appliedCount` (например, второй донор нажал одновременно), вернётся конфликт. Изменения не применяются, `rev` не меняется:

```json
{
  "ok": false,
  "conflict": true,
  "error": "Buff changed",
  "rev": 42,
  "epoch": "1700000000000abc",
  "buffs": [...],
  "history": [...],
  "givers": {...},
  "nicks": [...],
  "template": {...}
}
```

### Кеш и ревизия

- `state` и `history` кешируются в `CacheService`.
- `save` не удаляет кеш, а перезаписывает его свежими данными.
- `rev` и `epoch` хранятся в `ScriptProperties`; `rev` увеличивается на каждом `save`.
- Кеш считается валидным только при совпадении `rev` и `epoch`. Иначе данные читаются из таблицы.
- Чтение из кеша не берёт `LockService`; лок только на cache-miss и на запись.
- `?force=1` обновляет кеш данными из таблицы.

---

## Как это работает с фронтендом

1. При загрузке фронт показывает данные из `localStorage` (вместе с `rev` и `epoch`).
2. Если кеша нет или он старше 5 минут — сразу загружает `?type=state&force=1`. Иначе запрашивает `?type=version` и грузит `state` только при смене `rev`/`epoch`.
3. Все вычисления (`rankBuffsForQueue`, `applyBuffMath`, `generateCopyText`) делаются **на фронте**.
4. При применении баффа фронт сам считает новый `endAt`, `applied`, `appliedCount` и отправляет `POST ?type=save` с `buff`, `expectedAppliedCount`, `historyEntry`, `giverStat`.
5. При конфликте бекенд возвращает свежие данные, клиент откатывает оптимистичное изменение и просит повторить.
6. Бекенд просто записывает то, что дали.

## CORS

Google AppScript WebApp **не поддерживает** CORS-заголовки напрямую.

**Варианты решения:**

- **Прокси на уровне хостинга** — Vercel/Netlify могут проксировать запросы к GAS
- **CORS Proxy** — для локальной разработки
